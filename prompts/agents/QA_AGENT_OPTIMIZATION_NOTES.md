# QA & Auto Fix 优化说明：漏检问题与 Prompt 改进建议

本文档整理自实际故障复盘：应用因两类技术问题失败，而 `code_prototype_test_report.md` 与 `auto_fix_report.md` 均未指出这些故障。用于优化 QA Agent 与 Auto Fix Agent 的 prompt。

---

## 一、实际导致应用失败的两类技术问题

### 1. 浏览器安全限制（CORS / 模块加载）

- **现象**：应用使用 `<script type="module">` 加载 JavaScript。在本地通过文件夹直接打开（`file://` 协议）时，现代浏览器出于安全策略会阻止加载模块，导致 JS 完全无法加载，页面空白或不可用。
- **根因**：QA 未在“真实运行环境”下检查；仅做了语法与文件存在性校验，未考虑 `file://` 下模块被拦截的问题。

### 2. 逻辑导致的无限循环

- **现象**：在「自定义难度」设置中，校验未严格限制「地雷数量 ≤ 格子总数」。当尝试放置的地雷数超过可用格子时，放置逻辑会不断寻找空位，导致无限循环，浏览器卡死或崩溃。
- **根因**：QA 未对自定义设置等用户输入做边界/极端情况测试（如 mines > 格子总数），未发现会触发致命循环的无效状态。

## 二、报告漏检与已检内容对比

### 报告未发现的实际阻塞问题

| 问题 | 报告表现 | 原因简述 |
|------|----------|----------|
| **CORS / 模块加载** | QA 仅报「Syntax: PASS」、文件存在，未报运行失败 | 未在本地浏览器环境（`file://`）下验证；未识别「无 Web 服务器时 `type="module"` 会被拦截」 |

## 三、QA Agent Prompt 优化建议（已写入 qa_agent.j2）

为减少同类漏检，在 QA Agent 的 prompt 中应加入以下三类指令：

### 1. 运行环境与加载方式（Environment Simulation）

- **要求**：显式考虑**实际运行环境**。若应用预期被用户通过双击本地 `.html` 打开，则必须检查：
  - 在 `file://` 协议下是否会出现 CORS 或模块加载限制；
  - 是否存在 `<script type="module">` 等依赖 HTTP(S) 或本地服务器的用法；若存在，应记为 **Critical**（阻塞本地直接打开）。

### 2. 边界与极端情况测试（Boundary and Edge-Case Testing）

- **要求**：对**所有用户可配置/可输入项**进行边界与极端情况检查（可基于代码推理或静态模拟）。例如：
  - 校验数学边界：如「地雷数 ≤ 格子总数」「数值 ≤ 最大值、≥ 最小值」；
  - 零值、空值、最大值、最小值输入；
  - 确保这些输入不会导致：**无限循环**、除零、数组越界、或其它致命运行时错误。
- 若发现存在此类风险（如循环条件在极端输入下永不终止），必须列入 **Critical Issues**。

### 3. 致命错误优先（Fatal Error Prioritization）

- **要求**：在分类与排序问题时，**优先将「崩溃/卡死」类问题标为 Critical**：
  - 无限循环、未捕获异常导致页面白屏、脚本完全不加载（如 module 在 file:// 下失败）等，应优先于「缺失功能」列为 Critical，以便触发 Auto Fix 并优先修复。

---

## 四、与现有流程的关系

- **QA** 产出 `code_prototype_test_report.md`，其中 **Critical Issues Count** 与 **Critical Issues List** 驱动 **Fix Gate** 与 **Auto Fix**。
- 上述三条建议旨在让 QA 更早、更稳定地发现「环境不可用」与「逻辑致命错误」，从而让 Auto Fix 有明确条目可修，避免「报告通过但实际无法运行」的情况。
- Auto Fix 的职责与范围不变：仍仅根据 QA 报告中的 Critical Issues 进行修复；优化 QA 即间接提高 Auto Fix 的修复覆盖率。
